How it was done: eight independent reviewers each took one area (money, login, access to data, input and uploads, chat and sockets, web app, mobile app, server and deploy). They re-checked every earlier fix by trying to break it, and reported only problems they could show with a concrete path through the code. Every fix in this report has a test that fails on the old code and passes on the new.

Result: no critical code problem was found. The earlier fixes hold; the few partial ones are listed here and fixed. The only critical item left is the Azure secret in git history, which the owner must rotate.

Tests at the time of writing: backend 1,985 passed (one flaky queue test fixed since); web E2E 103 passed + 3 former failing tests now passing; mobile 13 checks and typecheck passing. The web typecheck is now clean (102 old errors fixed) and blocks CI; lint errors went from 209 to 56.

Money: SafePay, payouts, disputes, chargebacks

IDSeverityProblem, where, fixStatus
F1HighA re-resolved dispute could refund the customer twice
controllers/admin/disputesAdminController.js
What goes wrong: A refund times out but happened; the admin re-resolves with other amounts and a second refund goes through (133 paid out of 103 collected).
Fix: Refuse a new refund while another refund for the same dispute is pending, succeeded or unknown.
Fixed
F2HighA won chargeback blocked the payout forever
services/payout/releasePayoutToProvider.js, disputesAdminController.js, providerConnectTimeout.js
What goes wrong: Stripe keeps charge.disputed = true after the platform wins; every payout attempt failed and the provider was never paid.
Fix: Block only open or lost Stripe disputes (dispute status read from Stripe).
Fixed
F3MediumDispute on a payout with unknown outcome froze the money
safePayStateService.js
What goes wrong: The retry job and the admin both refused, so neither could finish.
Fix: A dispute cannot be opened or reopened while that payout is unresolved (max. 24 h).
Fixed
F4MediumA message or status change could undo a resolved dispute
disputeController.js, disputesAdminController.js
What goes wrong: Read-then-save overwrote "resolved" with an active status; the money stayed frozen.
Fix: Conditional update on the status that was read; 409 if it changed.
Fixed
F5MediumChargeback incidents could never close
stripePaymentIncidentController.js
What goes wrong: Reconciled only at the full charge (103) although the transfer was 97; a lost chargeback before payout had no way out.
Fix: Reconcile at min(charge, transfer); new admin action "close lost chargeback" (API only, no button yet).
Fixed
F6LowTwo admins could take back more than the chargeback
stripePaymentIncidentController.js
What goes wrong: The cap was read before the reversal; two approvals at once both passed.
Fix: Short lock on the Stripe dispute during the reversal.
Fixed
F7LowA transfer found later was only half recorded
releasePayoutToProvider.js
What goes wrong: Payout marked paid but Payment and money history not updated.
Fix: One shared "record recovered transfer" step for both paths.
Fixed
AUDMediumAdmin audit entries were silently lost
models/AdminActivity.js
What goes wrong: 19 action names (dispute resolve, refunds, chargeback recovery, shop changes) were not allowed, so the audit record was dropped without error.
Fix: Names added; a test fails if code logs an action the model does not allow.

Login, accounts and 2FA

IDSeverityProblem, where, fixStatus
A1MediumRevoked sessions kept receiving push notifications
models/Session.js
What goes wrong: After a password change, revoke or admin deactivation the stolen phone still got chat notifications.
Fix: Ending any session switches off its push tokens.
Fixed
A2MediumAn attacker could lock the real owner out of login
controllers/auth/loginController.js
What goes wrong: 100 failures for one email from many IPs blocked everyone, including the owner.
Fix: The email-wide limit only applies to clients that failed themselves.
Fixed
A3MediumUnlimited password guesses with a stolen session
controllers/users/profileController.js
What goes wrong: Email change and account delete checked the password with no limit; a hit gave full takeover.
Fix: One shared check with a limit of 10 wrong tries per 15 minutes.
Fixed
A4MediumAnonymous logins could stall the server
loginController.js, profileController.js, admin user creation
What goes wrong: Raw bcrypt calls skipped the bounded password queue.
Fix: All password checks and hashes use the bounded queue (503 when busy).
Fixed
A5LowPre-registered account: attacker payout/BankID survived the owner's reset
controllers/auth/passwordController.js
What goes wrong: An attacker who registered your email could keep their bank account and BankID on it.
Fix: New accounts without email proof are cleared on reset; accounts created before 26 Oct 2026 are not touched. Real fix: email verification at sign-up.
Fixed
A6LowAnyone could fill the reset-code budget
controllers/auth/authHelpers.js
What goes wrong: 20 wrong guesses blocked the owner's password reset.
Fix: Only misses count, per account and IP.
Fixed
A7LowA 2FA or backup code could be used twice in parallel
services/auth/mfa.js
What goes wrong: Parallel requests all accepted the same code.
Fix: Atomic use of the code; only one request wins.
Fixed
A8/Z4MediumA superAdmin could change another user's email
profileController.js
What goes wrong: Changing another admin's email, then resetting the password, took over the account with no audit.
Fix: Only the owner can change their own email; admin changes of verified/trusted are audit-logged.
Fixed
A9LowEndless 2FA guessing without warning
controllers/mfaController.js
What goes wrong: 6 tries per 15 min forever, nobody told.
Fix: After 20 wrong codes in 24 h the session ends and the owner gets an email.
Fixed
