Fixes in detail

P0 C2 · WebSocket refused from other websites

Problem: browsers do not apply CORS to WebSockets, so a page on any site could open a Socket.IO connection with a logged-in visitor's cookie and read their notifications and chats.

Fix: the Socket.IO server now refuses the handshake when the Origin is not in Jobblo's allowlist (allowRequest, reusing the same check as HTTP CORS). Requests without an Origin (mobile app, server) still connect.

Files: backend/bootstrap/socket.js · new test backend/__tests__/socketOrigin.test.js

Verified:

  • Test: foreign origin and lookalike origin refused (403); own origin and no origin accepted. Fails on the old code (2 of 4), passes on the new.
  • Live: https://evil.example refused · web app localhost:5173 connects · mobile (no Origin) connects.

P0 C3 · Private profile data no longer visible to other users

Problem: the “public” user projection was the owner's list minus three fields, so any logged-in user got other users' home address, earnings, last login, birth date, Google and Stripe ids; /users/top and search returned everyone's email, search matched on email, public lists showed members' emails, and completed-details showed both parties' emails before payment.

Fix:

  • New explicit allow-list PUBLIC_FIELDS (name, avatar, bio, skills, rating, city, portfolio, response stats…). The response cleaner keeps only these plus computed stats, so a query that selects more still cannot leak it.
  • Search no longer selects, returns or matches on email.
  • Public lists: emails only for the list's own members.
  • Order completed-details: emails only once the order is paid (same rule as the order list).
  • Search also returns only public jobs (allow-list instead of a blacklist) and caps page/limit (max 50).

Files: backend/utils/userProjections.js, backend/controllers/users/searchController.js, backend/controllers/listController.js, backend/controllers/orderController.js · new test backend/__tests__/publicProfilePrivacy.test.js

Verified:

  • Test: 8 cases; 7 fail on the old code, all pass on the new.
  • Live: another user's profile returns no private field but still the name · /users/top returns 0 emails (was 5 of 5) · searching by email domain finds 0 people · own profile still shows own email.

P1 H3 (part 1) · User search treats input as text

Problem: search text went straight into new RegExp(): (a+)+$ could stall MongoDB and ( returned a 500. Arrays (?q[]=a&q[]=b) also got through.

Fix: input must be a string, is trimmed to 100 characters and escaped with the existing escapeRegex in /users/search and /users/search-all. The public /filter/apply endpoint follows in part 2.

Verified: test cases for (a+)+$, ( and array input · live: all six requests return 200.

P1 H5 · Seed scripts can no longer wipe production

Problem: all 10 seed entry points empty collections (users, jobs, orders…) and read backend/.env, which on the server is the production database. One mistaken run would delete every user and create user1@jobblo.no as superAdmin with a password written in the repo. seeds/index.js also printed the full MONGO_URI.

Fix: one shared guard (seeds/guard.js) runs before every mongoose.connect in the seed scripts:

  • Refuses when NODE_ENV=production, even with confirmation.
  • Otherwise requires the database name as confirmation: --yes-wipe=jobblo-dev.
  • Logs only host and database name; the URI with credentials is no longer printed.
  • Note: a "local database only" rule would not help here, because production's MONGO_URI is also 127.0.0.1.

Files: new backend/seeds/guard.js; guarded seedData.js, seeds/index.js, seeds/run-*.js (6), seeds/seedNorwayLocations*.js (2); seeds/Readme.md updated · new test backend/__tests__/seedGuard.test.js

Verified: 9 tests, including starting the real seeds/index.js, run-categories.js and seedData.js with NODE_ENV=production: each exits with code 1 before connecting and never prints the password from the URI.

P1 H1 · Mobile: login links only accepted for a sign-in the app started

Problem: any app or web page can open jobblo://oauth-success?token=…. The app checked that the token was real and signed in as that user, even over an existing session. An attacker's link switched the phone into the attacker's account, so the victim's addresses and messages went to them.

Fix:

  • runOAuthSession records "this app started a sign-in at <time>" in memory and storage (survives Android restarting the app).
  • completeOAuthSignIn (the single place both iOS and Android finish a sign-in) accepts a link only within 10 minutes of that, and never while someone is signed in; the marker is cleared after a successful sign-in.
  • The check runs inside the single-flight sign-in, so two deliveries of the same real link still join one request.

Files: new jobblo-app/src/utils/oauthPending.ts (+ oauthPending.check.mjs), src/utils/oauthAuthSession.ts, src/hooks/useOAuthLoginCompletion.ts

Verified: 8 checks (fresh start accepted; no start, expired, future timestamp refused; never over a signed-in account) · app typecheck 0 errors. Longer term: replace the token in the link with a one-time code exchanged with PKCE, or verified App/Universal Links.

P1 H2 · Mobile: logout switches off push notifications

Problem: logout() ended the server session first, then tried to deactivate the push token with that dead session. The 401 was swallowed and the local key deleted, so the device kept receiving the previous user's chat notifications.

Fix: deactivate the push token first, while the session is still valid, then end the session.

Files: jobblo-app/src/store/authStore.ts

Verified: replayed both orders against the real API: old order → DELETE 401 and the token stays active; new order → DELETE 200 and the token is inactive.

P1 H3 (part 2) · Unused public filter endpoint removed

Problem: POST /api/filter/apply was public, ran the keyword as a regular expression, took page/limit from the body without a cap (limit: 1000000 dumped every listing), returned drafts, paid and completed jobs, dropped the location filter whenever a keyword was set, and put the raw error text in its 500 response.

Fix: neither the web app nor the mobile app calls it (only /api/filter/options is used), so the route, its controller function and its Swagger block were removed instead of patched.

Files: backend/routes/filter.js, backend/controllers/filterController.js

Verified: live POST /api/filter/apply → 404; GET /api/filter/options → 200; full suite green.

P1 H4 · One review per person per order

Problem: revieweeRole came from the request body and is part of the one-review-per-order unique index, so a party could rate the other person twice on the same order (once as seeker, once as poster).

Fix: the role is derived from the order (customer reviewing the provider → poster, provider reviewing the customer → seeker, the same mapping SafePay approval uses). A second review now hits the unique index and gets "Du har allerede gitt vurdering for dette oppdraget".

Files: backend/controllers/reviewController.js · test added to backend/__tests__/reviewEligibility.test.js

Verified: for both parties and every claimed role (seeker, poster, none) the stored role is the derived one; the new tests fail on the old code (2 of 11) and pass on the new.

Test stability · flaky queue test fixed

Problem: the "Redis down → fall back in-process" test timed the first load of the BullMQ library as well, which could exceed its limit while the full suite runs in parallel.

Fix: load BullMQ before starting the timer, so the test measures only the 3-second fallback. Verified: 3 full runs in a row, 1,651 passed each time.

P1 H9 · Setting up 2FA needs a code sent to the account's email

Problem: an admin or developer without an authenticator yet could set one up with only a password. Someone with a leaked password could add their own authenticator and then pass the 2FA gate for good.

Fix: new POST /api/auth/mfa/setup/send-code emails a 6-digit code to the account's address (refused when 2FA is already on; limited to 1 per minute and 5 per hour). POST /api/auth/mfa/setup returns the authenticator secret only after that code is checked for this user and this session, with an attempt limit. This reuses the existing developer step-up email code. The website's 2FA screen first asks "Confirm it is you" (email me a code, then continue), and only then shows the QR code.

P1 H6 · Money no longer gets stuck after approval or a failed transfer

Problem: three ways a paid job ended with the money held on the platform and nothing retrying it:

  1. Approval. The order is marked completed first. If a bookkeeping step after that (chat, listing, history, review, rating stats) failed, the request ended with an error before any payout existed. Approving again was refused ("already completed").
  2. Auto-release. If the 14-day auto-release payout failed and the retry job paid it later, the payment became released. The auto-release job only looks at completed payments, so the order stayed "waiting for review" for good, and the customer could still open a dispute on money that had already been paid out.
  3. Stripe errors. Any error from Stripe's transfer call set the payout to reconciliation_required, even when Stripe had clearly refused it. Nothing ever retried that state. The idempotency key was also fixed, so a retry within 24 hours would only have got Stripe's saved error back.

Fix:

  1. The bookkeeping steps after approval are isolated. A failure is written to the error log (APPROVAL_SIDE_EFFECT_FAILED) and the payout step always runs.
  2. Auto-release also accepts a released payment and then finishes the order. The retry job finishes the order as soon as its payout succeeds. One shared step does this (compare-and-swap, so it never touches an order a customer or dispute already moved).
  3. A clear refusal from Stripe (a 4xx answer other than 409) now means "failed, no money moved": the order lock is released and the retry job tries again. Network errors and 5xx answers stay "outcome unknown".
  4. Each attempt uses its own idempotency key. A second transfer is still impossible, because every retry first looks up Stripe for a transfer carrying this payout's id.
  5. The retry job (every 2 hours) now also checks "outcome unknown" payouts. If the transfer did happen, it is recorded. If, 24 hours after the attempt, Stripe still has no transfer for this payout, it goes back to "failed" and is paid on the next run.

One case is left for a person on purpose: if the provider has changed payout account since the attempt, the lookup could miss the old transfer, so the payout is never retried automatically. The daily money check still reports such orders.

Files: backend/services/payout/releasePayoutToProvider.js · backend/services/scheduler/jobs.js · backend/controllers/SafePayCheckoutController.js · tests: __tests__/approvalPayoutIsolation.test.js (new), __tests__/payoutReleaseRecovery.test.js, __tests__/safepayScheduler.test.js, __tests__/bug006_stripe_connect.test.js (now expects one key per attempt)

Verified: 13 new tests. Each of the three paths has tests that fail on the old code (8 in total). The fake Stripe in the tests replays saved answers per key, like real Stripe. The tests show:

  • A refused transfer is paid on the next retry.
  • An unknown outcome is kept for 24 hours, then paid exactly once.
  • A transfer that really happened is only recorded, never paid twice.
  • A payout account that changed blocks the automatic retry.

Full backend suite: 1,671 passed. The local backend boots and the scheduler starts on the new code, and the retry job ran cleanly against the local database (no stuck payouts there to replay).

P1 H7 · Every dispute ends with money and order status in step

Problem: four dead ends in the admin dispute flow:

  1. A reopened dispute kept its old resolution, so it could never be resolved again, and the payout stayed frozen.
  2. An admin could set a dispute to closed or cancelled without resolving it, which left the order disputed with no way out.
  3. On a paid-out order, the customer was refunded before the provider's transfer was reversed. If the reversal then failed (the provider had already been paid out), the platform paid the money twice.
  4. A "full refund" returned only the job price, not the 3 % fee the customer had also paid.

Fix:

  1. A dispute now ends only through "Resolve". The status endpoint refuses resolved, closed and cancelled; the admin web app never used it for those.
  2. Reopening clears the old resolution and puts the order (and payment) back under dispute. It uses the same safety checks as opening a dispute: not while a payout or start-deadline refund holds the order, and not if another dispute is active.
  3. A resolution that has already moved money (a refund, transfer or reversal) cannot be reopened, so money can never move twice; that needs a manual correction in Stripe. Old cancelled dead-end disputes can now be reopened, and the admin page shows the button for them.
  4. The provider's transfer is reversed first, and the customer is refunded only after that succeeds. A failed reversal refunds nothing and leaves the dispute open to retry.

Decision made (policy): a full refund (full_refund_to_customer and cancel_without_payment) now returns everything the customer paid, the 3 % fee included. This is the same as the existing start-deadline refund, and it is the customer-safe choice. To keep the fee instead, change paidTotal back to securedAmount in disputesAdminController.js.

Files: backend/controllers/admin/disputesAdminController.js · frontend/src/pages/SuperAdminDashboard/DisputeDetailPage.tsx · test: backend/__tests__/disputeResolutionMoney.test.js

Verified: 11 new tests, all failing on the old code. They cover:

  • A full refund includes the fee.
  • The reversal runs before the refund, and a failed reversal refunds nothing.
  • Status changes cannot end a dispute.
  • Reopen, then resolve again, works; reopen is refused after money moved, while the order is locked, or with another active dispute.

The 16 existing dispute tests still pass.

P2 M1 · Error responses no longer leak internal messages

Problem: controllers answered 500 errors with error.message, which sent raw MongoDB and Stripe text to the client (collection names, ids, and e-mail addresses inside duplicate-key errors). Every unknown URL (404) was also logged as INTERNAL_SERVER_ERROR, and the error logs never expired.

Fix:

  • One helper, utils/serverError.js, writes the full error to the log under the request id and answers with a safe message plus that id (referenceId), so support can find the log entry. It replaces 40 raw responses in 11 controllers.
  • For catch-alls around a create or update, a sibling helper answers a validation error with 400 and its message (the problem is in the caller's input), a cast error with a neutral 400, and anything else with the safe 500.
  • Where an error has its own status (a refusal our code made on purpose, such as a wrong 2FA code), its message is kept. Otherwise it goes through the helper.
  • The central error handler no longer logs 4xx errors as server errors.
  • A client-sent X-Request-ID is only echoed back when it is short and plain (at most 64 letters, digits, - or _).
  • Error entries now expire after 90 days, in both ErrorLog and the error part of AdminActivity. The audit trail is kept.

Files: utils/serverError.js (new) · middleware/errorHandlers.js · middleware/requestId.js · middleware/auth.js · models/ErrorLog.js · models/AdminActivity.js · 20 controllers · test __tests__/safeErrors.test.js

Verified: 9 tests. They check that:

  • No response contains duplicate-key or cast-error text.
  • The request id is in the response and in the log.
  • A 404 is not logged.
  • A spoofed request id is replaced.
  • A scan of every controller fails the build if a raw .message is ever sent with a 500 again.

Both TTL indexes are built on the local database, and the full backend suite passes.

P2 M10 · Webhooks from both Stripe modes are processed

Problem: the webhook took its signing secret and Stripe client from the global STRIPE_TEST_MODE switch. After a switch, the other mode's events (live refunds, chargebacks, transfers) failed the signature check or were rejected as a "mode mismatch". Stripe stops retrying after about 3 days, so they would be lost. A paid checkout from the other mode was also sent to manual review.

Fix:

  • The signature is checked against both signing secrets, test and live.
  • The event's own livemode must match the secret that verified it.
  • The event is then processed with that mode's Stripe client. If that mode has no API key, the answer is 503 so Stripe retries.
  • Duplicate handling (StripeEvent) is unchanged.
  • Checkout confirmation compares the session with the order's own mode, not the switch.

Files: backend/config/stripe.js · backend/services/stripe/webhookDispatcher.js · backend/controllers/SafePayCheckoutController.js (mode check only) · tests stripeWebhookBothModes.test.js (new), confirmPaidSessionIdempotency.test.js, stripeWebhookDispatcher.test.js

Verified: 6 new tests use real Stripe test signatures. With the switch on test, a live refund is processed with the live client. The old code fails that test. A forged event is refused, and so is an event signed with the wrong mode's secret. 52 tests in the three Stripe suites pass; I re-ran them myself.

Owner action: set all four on the server: STRIPE_WEBHOOK_SECRET, STRIPE_TEST_WEBHOOK_SECRET, STRIPE_SECRET_KEY and STRIPE_TEST_SECRET_KEY. If Connect events go to a separate Stripe endpoint, that endpoint has its own secret, which is not supported yet; today it must be the same endpoint as the platform one.

P2 M2 · Every list endpoint has a page limit

Problem: about 20 endpoints used limit/page exactly as sent, or returned the whole collection: favorites, lists, orders, job requests, reviews, applicants, a user's listings, notifications, transactions, blocked users, admin lists, and others. A huge, negative or text value loaded entire collections or caused 500s.

Fix: the shared parsePagination helper is used everywhere. It accepts whole numbers only, caps the limit at 100, and allows page 1–1000 (the page cap is new). Bad input is clamped to a safe value, not refused, so existing clients keep working. Where the web or app expects every item, the default page size is 100, and response shapes are unchanged. List endpoints that had no order are now sorted newest first, so pages are stable. The admin transaction search now treats its input as plain text, not a regex.

Files: utils/pagination.js, plus these controllers: favorites, lists, orders, reviews, applicants, notifications, transactions, blocking, admin and my-applications; test listBoundsAndAuthz.test.js

Verified: each endpoint, called with limit=99999999&page=-5, queries at most 100 items. The tests fail on the old code.

Not capped on purpose: the owner's own "my posted jobs" and applicants overview, where clients need the full list.

P2 M6 · Smaller authorization gaps closed

P2 M5 · Sessions and sockets (and the chat parts of M2, M4, M6, M7 and P3)

  • Old refresh token: the grace window used updatedAt, which every request changes, so an old token kept working. It now uses a separate rotatedAt. Reusing an old token outside the 60-second window is treated as theft: the session is deleted and its sockets are disconnected. Inside the window, the current token is returned without rotating again.
  • Sockets after logout: every socket joins a session room. Hooks on the Session model disconnect a session's sockets whenever that session is deleted, which covers every place that ends a session:
    • logout, and revoking one or all sessions;
    • password change and reset;
    • admin deactivate and revoke;
    • self-delete, and the refresh-theft case above.
    An admin soft-delete now also deletes the user's sessions. This works across servers through the Redis adapter.
  • One message check: the HTTP route and the socket now share one send function. It checks the text (non-empty, at most 5,000 characters), that the sender is a participant, the block list in both directions, a limit of 30 messages per minute per chat, and a chat size cap below MongoDB's 16 MB (a full chat answers 409).
  • Presence: each user receives only their own chat partners' online status, not every online user's id.
  • Blocking now works (M4): it stops creating a chat, sending chat and order messages, and applying to the other person's job.
  • Order messages (M6): only the order's parties can mark a message read, and clients can no longer send "system" messages.
  • Lists (M2): chats and messages are paged; the default page is 100.
  • Agreed price (P3): must be a whole number of NOK from 1 to 1,000,000, and only the job owner (the payer) can set it.

R2 Login and account security: second-round fixes

  1. High: anyone could log out any user. A cookie written as j:{"$ne":null} was parsed into a database operator, so POST /api/auth/logout deleted a random session, or a chosen user's. Every cookie value that is not plain text is now dropped right after parsing, and the logout and refresh handlers only accept text.
  2. Email code guessing: parallel guesses at the 2FA-setup / step-up email code all counted as one attempt. The attempt is now spent atomically before comparing; 20 parallel guesses get at most 5 checks.
  3. Account pre-hijack: an attacker who registered your email and linked their own Google or Vipps login could still sign in after you reset the password. A password reset now removes linked logins, and the owner re-links them. The real fix is email verification at registration, still to do.

  5. Lockout: anyone could lock any account. The lockout now counts per email + IP (10 failures), with a much higher limit per email (100 in 15 minutes), so the real owner can still log in from their own connection.
  6. Vipps and BankID linking: a link started by one user, followed by a logout, could be completed by another person in the same browser. The callback now requires the same signed-in user and session.
  7. Token order: the access cookie was read before the Authorization header, so a stale cookie in the phone app could make user B's requests run as user A. The header now wins, with the cookie as the fallback (socket too).
